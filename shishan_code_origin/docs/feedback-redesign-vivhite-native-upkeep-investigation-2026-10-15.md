# 白绮维护费下限与原生免付开关调查

## 实机事实与调查范围

主任务在 rc5 `20261015T084453Z` 观察到：n=1，白绮领袖页维护费为 1.0，另外四名常规领袖均为 4.0；证据为 `rc5-white-before-leaders.jpg`。当前生产特质使用本人 `leaders_unity_upkeep_mult=-1`，故「-100% 修正」不能据此写成「本人实际费用为零」。本次仅只读调查，未改冻结 Mod、游戏状态或验收主记录。

## 当前 4.5.2 原版依据

- `common/defines/00_defines.txt:2031`：`NEconomy.MIN_MODIFIER_MULT=-0.9`，注释明确用于避免各种倍率到零或负值。
- 同文件 `:2032`：`MIN_ECONOMIC_MODIFIER_MULT=-0.9`，注释明确经济类别生成的成本、维护和产出修正不能低于此值。`leaders` 正是在 `common/economic_categories/00_common_categories.txt:1090` 生成维护倍率的经济类别。
- `common/inline_scripts/paragon/leader_base_upkeep.txt:12` 默认凝聚力维护为 `unity=2`、`mult=trigger:has_base_skill`。普通等级 5 的基础为 10，最低 10% 为 1，等级 2 基础为 4；这与当前画面吻合。这里只证明原版下限与观测一致，不把它当作已导出全部国家正倍率的完整计算追踪。
- `common/game_rules/00_rules.txt:417` 明确标注 `This=leader`，`:418` 定义 `should_pay_for_leader_upkeep`。其 NOR 在 `:428` 排除 `has_leader_flag=should_not_have_upkeep`。这是原生是否付费规则，而不是另一个百分比修正。
- 原版 `common/relics/relics.txt:2377` 的 `create_leader` 在结果领袖的 `effect` 中于 `:2390` 设置 `set_leader_flag=should_not_have_upkeep`，证明该开关实际用于原版无维护费领袖。
- 本次原生生成的 `effects.log:1212` 明确 `set_leader_flag` 支持 leader。无需新增 opcode、覆盖 game rule、改 defines 或替换原版领袖类别。

没有发现能由巨额负倍率绕过上述下限的依据，因此不建议用 -999999% 或同类数值。原版 `leader_resource_upkeep*.txt` 还提供类别维护加算；即使简单抵消默认基值，也不等价于原生免付规则，不能用一条静态负值保证所有等级、国策和修正下都免费。

## 可行机制及范围差异

建议在白绮创建与重启的结果领袖上显式设置原生 `should_not_have_upkeep`；旧档通过现有白绮刷新入口只遍历 `has_leader_flag=shishan_code_vivhite` 的受雇领袖并幂等补旗标。不更改其余领袖，不重建既有领袖，不依赖维护次数或等级。可在后续实施时撤掉已经无法表达真正免付的 -100% 修正，并同步准确说明。

该原生旗标语义是**白绮本人免付领袖维护资源**，不只免凝聚力。当前个体机械普通维护资源为凝聚力，因此能满足当前费用场景；具有额外能源、合金或其它领袖维护规则的国策下，开关也会免掉她本人的相应资源。若设计必须严格保留她的非凝聚力维护，这一方案需要明确取舍，不能伪称为「只免凝聚力」。候选生产修改须由主任务决定，本文没有实施。

最小原生诊断命令为 `effect every_owned_leader = { limit = { has_leader_flag = shishan_code_vivhite } set_leader_flag = should_not_have_upkeep }`。此命令只供主任务在独立诊断分支验证原生开关，必须标注受控效果，不能把它作为冻结生产包已经修好的证明。
