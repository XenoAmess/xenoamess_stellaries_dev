# 开发验收交给另一台机器的困难评估

日期：2026-10-06。调查基线为提交 `3255af27490b4532c7d19063795812d809e35e64`、Mod `0.2.0-rc.1`。本轮只读调查并记录结论，不修改 Mod、夹具或工具，不启动游戏或桌面自动化；没有在第二台机器实际执行。下文区分源码确认的事实与交接建议，不把可迁移性判断写成异机验收通过。

## 判断

可以交接。现有程序性检查迁移难度较低；补齐依赖和同版本游戏资料后，包级静态检查迁移难度中等；完整实机/UI/存档/自然体验验收难度较高。当前并没有一套安装后自动跑完新版全部矩阵的交接入口，另一台机器需要承接尚未完成的验收开发，而不只是重复现有 PASS。

| 验收部分 | 可直接带走的内容 | 主要前置与困难 |
| --- | --- | --- |
| 32 项 Python 回归 | 仓库中的测试、标准库检查器与生产脚本 | 完整检出仓库、固定 Python 版本；这些只是离线合同/负例，不需要桌面。 |
| open_kaishek 首道包级检查 | 已记录工具提交、命令和旧报告 | 工具是另一仓库，JAR 不在本仓库；需要工具构建、Java 运行环境与匹配的游戏资料。 |
| 原版本地化/候选身份检查 | `--game` 参数及已记录检查范围 | 要有本机原版数据；省略 `--game` 会跳过外部本地化引用核对，不能等价替代原先结果。 |
| 原生经济、物种克隆、存档重载 | 详细方案与部分历史存档 | 新版尚无完整实机夹具；必须实际加载新版、制作前后存档并验证状态，不继承旧版 PASS。 |
| 长名称 UI、OCR、自然体验 | 中文用例和历史操作经验 | Windows 交互桌面、游戏/DLC、显示与截图校准，以及人工观察；当前禁止启动游戏的约束仍有效。 |

## 具体困难与证据

### 1. 必需工具属于另一仓库，干净机器缺少构建产物

本项目规则要求先用 `open_kaishek`。开发记录使用其提交 `522ac2d93bd6c534a6a242a227057de40a8977c1`；调查时该工具仓库 HEAD 仍为此提交。它不是本仓库的子模块，也没有随 Mod 提供 CLI JAR。工具默认读取自身目录下 `kaishek-cli/target/kaishek-cli-0.1.0-SNAPSHOT.jar`；`git ls-files kaishek-cli/target` 没有输出，不能指望 clone 后已有 JAR。

工具 README 要求 JDK 21、Maven 3.6.3 或更高。其推荐静态入口首次构建可以使用 `--online`，已有依赖缓存才能可靠使用离线 Maven 构建。交接需要另行获取该工具仓库、冻结提交、按其说明构建验证，或提供可核验的对应构建产物；不能只复制 Mod 和旧 PASS 报告。入口支持 `--cli`，可指定实际 JAR 位置。

上述来自本机工具的 README、pom.xml、`tools/accept_stellaris_mod.py` 和 Git 查询；本轮没有重建或修改工具。如果后续真正验收发现缺陷，依项目规则先修复并验证工具，再继续 Mod 验收。

### 2. 游戏身份固定，安装“4.5.*”不等于重现原环境

历史基线为 `Cygnus v4.5.1 (358e)`，EXE SHA-256 为 `6fe06709f265e726722dc23f617c5fc4e5557629e2d43fe312016aba547c83e4`。open_kaishek 的入口默认检查这个指纹，并固定寻找传入游戏目录中的 `stellaris.exe`。另一台机器若装了不同补丁/平台构建，可能先得到 `GAME_EXE_IDENTITY`，即使 descriptor 的 `supported_version=4.5.*` 仍匹配。

`--expected-exe-sha256` 可以表达另一份已确认的输入身份，但简单替换为新 EXE 指纹不能证明旧数值、原版特质、岗位或存档合同仍适用。应当明确是复现原基线，还是建立新版兼容基线，重新核对相关原版资料与预期。Linux/macOS 上 Python 离线检查与 Java parser 的可移植性，不能等同于当前这条 Windows EXE 包级入口和桌面实机链路已经支持这些平台。

实机还需要记录实际 DLC/机械政体/飞升可用条件。只复制脚本不一定能复现同一合法帝国和存档内容集。本轮没有查询最新 Steam 版本，也不把历史版本称为当前最新版本。

### 3. 新程序检查较易迁移，旧桌面入口存在具体耦合

[新检查器](../tools/validate_feedback_redesign.py)、[32 项测试](../../tests/test_shishan_feedback_redesign.py)和[奖励合同 audit](../../tools/shishan_code/audit_reward_contract.py)通过 `__file__` 推导仓库根目录，使用标准库或仓库内模块；检查器接受 `--mod`、`--game`、`--report`，奖励 audit 接受 `--game`。因此不要求目标仓库仍放在 `C:\workspace`。现有命令中的绝对路径主要需要重新绑定，不能笼统认为所有检查器都写死了本机路径。

本机 Python 实际为 `3.14.7`；代码使用 `zip(..., strict=True)`、`Path.write_text(..., newline=...)` 等接口。没有跨 Python 版本/系统矩阵，不承诺任意旧版 Python 可运行。`requirements-acceptance.txt` 属于桌面/OCR 依赖，不是跑这 32 项离线测试的必要条件。

旧实机入口的情况不同：

- [launch_probe.py](../../tools/shishan_code/launch_probe.py)确实针对本 Mod，但游戏路径写死为默认 C 盘 Steam 安装目录，只提供 `--id`；它依赖 Windows `LOCALAPPDATA`，设置为所有已安装 DLC 启用并创建隔离 userdir。它是启动探针，不是新版全用例执行器。
- [stellaris_acceptance.py](../../tools/stellaris_acceptance.py)默认目标是 `vivhite_infinite_positions`，冻结的 Mod 指纹也不是本起源候选；不能把它直接当成本 Mod 已配置好的入口。虽然游戏/Steam路径部分支持环境变量，DirectX redist CAB 路径、默认分辨率等仍有本机配置。
- 上述桌面工具导入 `pywin32`、PyAutoGUI、RapidOCR等，并有 Windows 输入/窗口调用。依赖版本虽已列出，但全新机器仍需要安装与验证这些组件，不能因新检查器使用标准库就认为整个实机链路没有环境依赖。

### 4. Git 带走了精选历史证据，没有带走本机全部运行状态

调查时 `assets/shishan-code-origin/evidence` 有 **388 个 Git 跟踪文件，共 294401024 字节（约 280.8 MiB）**，其中包括历史原生存档和图片。这部分可以随仓库交接。耗尽存档 `shishan_reward_exhausted.sav` 的实际 SHA-256 再次核对为 `554504e65d4b14d70fd91be3cb66c434c7c232ea37c109e70b7e2ebe93f4fccf`，与方案一致。

但 [.gitignore](../../.gitignore)明确排除 `_runtime/`，`git ls-files _runtime` 为 0；隔离 userdir 又在本机 `LOCALAPPDATA` 下。临时夹具、未精选的完整日志、截图、进程记录和加载副本不会跟随 clone 自动到达另一台机器。新机器上的路径/PID/窗口句柄也不能沿用旧运行清单。

应按用例挑选需要的原生存档、夹具源码和原始证据，建立相对路径/哈希清单，决定哪些重新生成、哪些另行归档传递。现有新版方案 F-START/F-TRAIT/F-ECON/F-CHOICE/F-PROJECT/F-LEGACY/F-LATE/F-STRESS/F-NAME 仍包含未来夹具需求；不能认为历史证据目录已经覆盖这些新版场景。

### 5. 有些旧审计检查的是旧版本，不能原样套到新候选

例如 [audit_resource_source_saves.py](../../tools/shishan_code/audit_resource_source_saves.py)仍以 III 阶段 `0.75`、V 阶段 `0.25` 的旧产出倍率核对历史存档；新版对应孤立阶段倍率为 `0.875`、`0.625`。[audit_pr05_reward_exhaustion.py](../../tools/shishan_code/audit_pr05_reward_exhaustion.py)仍验证旧四类迭代计数增长；新版冻结旧计数、耗尽后改增 R。[audit_sv01_stage1_reload.py](../../tools/shishan_code/audit_sv01_stage1_reload.py)还冻结了具体历史文件名、日期和状态值。

这些脚本保留用于历史证据审计有意义，却不是新版通用测试 runner。另一台机器直接“把所有 audit 都跑一遍”，可能得到旧历史检查通过，却没有验证新机制；也可能用旧预期误报新候选失败。交接清单必须明确每个入口的版本、输入存档和适用用例，新增新版审计前先写设计。

### 6. UI 自动化与机器显示/输入环境关联很强

[实机经验](../../docs/stellaris-runtime-testing.md)已有实测问题：DPI导致坐标偏移、中文输入法吞空格、窗口未正确绘制、ImageGrab返回旧桌面、滚轮单位错误，以及 OCR 命中提示框中重复标题。本机曾用 Steam 物理 F12、1024×768 窗口和 ClientToScreen解决部分截图/坐标问题，这些是本机经验，不能作为另一台 GPU、驱动、远程会话或缩放配置的已验证方案。

另一台机器应先建立一个最小可靠闭环：有效游戏帧→中文文字/坐标识别→一次操作→可见状态与日志复核，再跑长名和存档矩阵。自动化需要可交互桌面，普通无桌面 CI 不能沿用当前 Win32 操作链路。GPU/远程桌面的具体影响属于需验证风险，本轮未对第二台机器实测。

同一交互桌面的鼠标、键盘和焦点是共享资源，不宜让多个 agent 或多个验收进程同时操作。程序性检查可以并发；实机并发应采用独立机器/桌面/虚拟环境和各自隔离 userdir，每个桌面安排一个操作执行者。不同 CPU 推进游戏日期的速度也不同，不能照搬本机固定等待秒数作为“项目已完成”的证明。

### 7. 当前合同有未完成目标，新接手者需要识别验收边界

目前包级与五组离线合同检查通过，**不代表引擎完整行为通过**。以下情况必须在交接入口提前明确：

- 5% 当前是原生岗位产出加算，独立乘算目标尚未实现；不能要求现候选通过 TS-06，也不能把 TS-06偷偷改成加算通过。
- 白绮自身使用 -100% 凝聚力维护修正；叠加其它正维护倍率后严格零费用没有结论。
- 全名18字/54字节仅静态完整；实际截断/换行/遮挡未验证。
- 真实物种克隆、国内与外国共享模板隔离、窗口存读档恢复、项目原生队列、自然路线和性能还未通过本轮实机检查。离线解释器有明确抽象 hook，不能据其 PASS 给这些项目签字。

若下一台机器继续遵守当前“不启动游戏、不操作屏幕”的限制，它也只能完成静态/程序性范围，无法补出上述实机结论。转移执行地点本身不改变授权范围。

### 8. 文件身份和证据算法需要统一

当前候选90文件的程序检查器 tree SHA-256为 `230b87c89debfcf202ee47e7efc51cf5418e01ba8cb64734d935367097dfa696`。生成器已固定LF，中文本地化仍须保留UTF-8 BOM。但仓库没有跟踪的 `.gitattributes`，另一台机器的 Git 换行设置、编辑器或打包工具仍可能改变工作树字节，造成指纹不同，即使语义未变。不能用“哈希不一致”直接推断玩法错误，也不能忽略真实包内容变化。

此外，新检查器按“相对路径+NUL+每文件SHA-256原始digest”聚合，而旧桌面 harness 按“相对路径+NUL+文件原始内容”聚合，两个都叫 tree hash，却不是同一算法。交接必须记录计算入口/算法及范围，用同一入口比较同一个包；JSON 中本机绝对路径变化也不应当作功能失败。报告写到包外，避免报告本身被计入下一次包指纹。

## 建议的交接顺序

1. **先冻结输入和验收范围。** 使用上述 Mod 提交/版本、工具提交、游戏身份/DLC、简体中文运行时范围，列明当前加算实现和未完成目标。更换游戏基线时建立单独记录，不冒充原基线复现。
2. **先交接程序性验证。** 目标机配置 Git/Python/JDK及工具产物，用真实目标路径依次跑 open_kaishek、32项测试、带`--game`的新检查器和奖励audit；结果写到独立新run目录。报告旧PASS与新执行分别保存。
3. **完整实机交接前补执行入口和夹具清单。** 将路径、版本/指纹、显示、截图后端等转为明确配置；绑定本起源候选，区别历史audit与新版断言；按新方案准备并验证需要的原生存档和P语言夹具。此项是后续开发建议，本轮未施工。
4. **最后建立桌面闭环并跑功能/体验矩阵。** 先测真实克隆、窗口重载和经济来源等引擎缺口，再测长名多缩放与自然局；每台机器独立输出manifest、日志、存档、截图/OCR及case结果。自然体验和功能验收分别报告，不靠简单拷贝历史结果收口。

目前不建议把“另一台机器clone后自动全绿”当作交接验收标准。可落地的第一步是重现程序性检查；完整实机阶段需要补齐可执行的新版环境/夹具/操作链路。未在第二台机器试运行，因此没有提供设备准备时长、游戏运行耗时或异机PASS承诺。

## 2026-10-07 补充：执行时间预估

用户追加要求估算开展验证需要多久。以下为排期估计，不是第二台机器实测耗时或保证通过的承诺。假设一名熟悉本仓库的执行者、一台可独占交互桌面的 Windows 机器、游戏及必需 DLC 可取得、依赖下载正常，且没有需要重写核心机制的严重缺陷。一个工作日按约 6—8 小时有效投入计算；桌面运行期间仍有游戏推进、人工决策和证据采样，不能全部当作无人值守后台任务。

### 按交付深度估算

| 验证范围 | 预估投入/排期 | 交付边界 |
| --- | --- | --- |
| 复现现有程序检查，目标机依赖和游戏资料已齐 | 2—4 小时 | 包级工具、32项回归、带原版资料的合同/候选/翻译检查、身份与报告核对。脚本实际运行在本机为秒级至分钟级，大部分时间用于检查环境、输入和证据。 |
| 同上，但从干净机器开始配置 | 半天—1工作日 | 包括Git/Python、外部工具构建/Java、路径和游戏资料核对；不含安装/下载游戏的未知等待。 |
| 首轮重点实机验证 | 2—4工作日 | 优先真实克隆与外国隔离、奖励/reroll、项目恢复、关键读档、5%实际加算效果、长名默认布局；用于发现阻塞，不能称完整矩阵通过。 |
| 现有完整方案：功能、迁移、长名多显示配置、压力与22局自然体验 | 7—12工作日，排期建议预留2—3周 | 包含新版夹具/执行链路准备、两政体适用核心矩阵、自然局和完整报告；原设计未实现目标仍单独列出，不伪造PASS。 |

完整范围的大致工作量分配：环境与身份半天—1天，新版实机入口/夹具准备2—3天，功能/迁移/UI/压力矩阵2—4天，自然路线3—5天，整理证据与相关复验半天—1天。部分夹具、报告和自然局可以交错开展，因此这些阶段不能机械相加为最终日历工期；也不能用并行静态测试消除桌面操作和自然局的耗时。

自然体验是长尾：方案明确要求22个独立开局，另有V后维护/清理分叉；候选无维护路线理论约79.17游戏年进入V，随后最多再观察20游戏年。不同硬件、星系大小、外部战争和采样频率会改变实际小时数，目前没有新版自然局实测吞吐。上述3—5天是工作量预留；开始后应先跑一条正常路线和一条拖延路线，测出真实执行/采样速度再更新总排期。

### 并发与返工

若有两台独立可交互机器并安排独立执行者，已准备的矩阵可按政体/自然路线拆分，完整范围可以争取5—8工作日；这是条件性估计，共用的夹具开发、环境问题和最终证据复核仍在关键路径上。同一桌面增加agent数量不会等比例缩短UI验收时间。

小缺陷的定位、修复与受影响复验另预留2—4工作日；如果游戏版本不匹配、截图链路无法工作、缺必需DLC或出现广泛克隆/存档问题，先按具体阻塞重新估算，不承诺该缓冲能覆盖。

上述时间不包含“开发出真正独立乘算渠道”或“实现叠加其它倍率后仍严格零维护”的新增开发。这两项目标目前没有完整可行性证据，不能给出保证全部原设计PASS的固定日期。若要求完整原设计收口，须先解决或明确修订这些目标，再重新冻结验收范围。若仍禁止启动游戏/操作屏幕，则可执行范围仅为前两行，后续实机工期尚不能开始计算。
