# Stellaris 实机自动化经验

本文记录本项目在 Stellaris 4.4.6 上已经实测确认的 UI、存档和日志行为。它们属于 Stellaris 专有实践，不同步到 CK3 方言知识库。

## 语言范围

- 后续所有实机、UI、OCR、存档重载和运行时回归只使用简体中文（`l_simp_chinese`）。
- 英文及其他语言仍可维护翻译，但只检查本地化键完整性、文件头与编码、引用一致性、原始 key 泄漏风险和简体中文占位文本，不启动对应语言的游戏。
- 非中文翻译结果必须标记为静态校验结论，不能沿用 `LOAD-GREEN` 或 `SCENARIO-GREEN` 等运行时通过术语。

## 输入优先级

1. 优先发送物理扫描码。普通虚拟键在 Stellaris 中可能没有效果；已确认 Esc 使用扫描码 `0x01`，回车使用 `0x1c`，空格使用 `0x39`，F7 使用 `0x41`。
2. 有稳定文字目标时使用 OCR 点击，例如主菜单的“保存游戏”“读取游戏”和“退出到桌面”。
3. 只有对象没有快捷键或稳定文字入口时才使用坐标，例如具体星球、窗口关闭按钮和决议列表滚动条。
4. 2560×1440 截图可能在查看器中缩放到 2048×1152。动作坐标必须使用原图/OCR JSON 坐标，不能从缩放后的预览图直接抄坐标；自动化进程还必须在第一次截图/输入前声明 Per-Monitor DPI awareness，否则 Windows 125% 显示缩放会把 OCR 物理像素坐标映射到约 80% 的实际点击位置。运行 `20260906T090503Z` 已通过“滚动决议列表无效、拖滚动条却移动整个窗口”复现该问题。
5. 直接启动后若 Stellaris 窗口已前台但画面透明、仍露出桌面，发送物理 `Alt+Enter`（扫描码 `0x38` + `0x1c`）可强制切换显示模式并恢复绘制。运行 `20260906T041510Z` 已复现并用此方法恢复；恢复后再继续截图，不能把透明帧判为游戏未启动。
6. OCR 点击会在鼠标悬停后同时识别决议卡片标题与提示框中的重复标题。若 action 记录的命中坐标落在决议窗口之外，点击并未执行决议；应先把指针移出提示区域，再按已由 OCR 固定的卡片坐标点击，并以状态变化和日志复核。
7. 需要清除提示框但保留当前窗口时，可在窗口外安全区域执行 `scroll 0`，只移动指针而不点击；点击空白区域可能直接关闭决议或殖民地窗口。
8. 不应仅凭发送 F5 就宣称快速存档成功；运行 `20260906T053229Z` 未观察到 F5 生成文件。回归夹具应通过暂停菜单进入“保存游戏”，并在文件系统中核对 `.sav` 的名称、字节数和 SHA-256 后才记录成功。
9. 4.4.6 中文环境下，控制台会与 `-debug_mode` 的 F7 调试面板争夺键盘焦点。运行 `20260906T081506Z` 中字母可输入，但空格、Enter、退格被错误路由，`minerals 5000` 最终成为 `minerals5000` 并返回 `Unknown command`。资源前置条件优先通过自然积累或夹具初始状态满足；若必须使用控制台，必须先截图确认完整命令（含空格），再截图确认成功回显与资源变化，不能只按动作日志判定成功。
10. `console.gui` 定义表明控制台输入框位于窗口 `(30,100)` 内的相对 `y=310..350`，即当前 2560×1440 布局约为绝对 `y=410..450`；历史区 `y<405` 不会取得输入焦点。中文微软拼音状态还会吞空格并截获删除/提交键，实测先按一次 `Shift` 切到英文状态后空格才会进入文本；清空与提交仍应用物理扫描码 `0x0E`、`0x1C`。
11. 游戏自带 `tools/commands_at_date.txt` 明确支持把文件复制到 userdir 后按游戏日期执行控制台命令，并且过期日期不会补执行。自动验收应在启动前把所需命令写进隔离 userdir、选择未来日期，并在 manifest 中冻结；这比在中文控制台 edit box 中模拟文本稳定，也不会污染玩家真实目录。
12. 右侧概览可能让星系组标题和殖民地子项使用同一名称。OCR 的“按文字点击”会优先命中上方组标题，只完成居中而不打开殖民地；应从 OCR JSON 选择同名的下方子项坐标，或对已固定的子项执行第二次精确点击，并以殖民地窗口出现作为成功条件。
13. 种子存档即使是有效 ZIP，也可能因当前游戏内容集或云状态在载入列表中呈红色并禁用“载入”。运行 20260906T152520Z 遇到该情况后改用全新原版预设开局完成政体负向矩阵；禁用载入按钮应记录为种子不可用，不能冒充已完成重载，也不应阻塞可由新游戏等价验证的可见性场景。

## 方舟殖民地导航

- F7 的“殖民地和星域”列表不列出游牧方舟殖民地，不能把“列表为空”解释为方舟不存在。
- 可靠入口是展开右侧概览的方舟组，选择方舟实体，再点击殖民地名“首都方舟”。若“首都方舟”子项尚未展开，可先点击星图中的方舟实体，使右侧条目展开后再按文字进入。方舟载体使用 `pc_ark` 并复用标准“决议”窗口，但 4.4.6 实机日志证明该窗口执行决议时 root scope 是 `ship`，不是普通殖民地的 `planet`；新增 flag/effect 必须支持两种 scope。
- 决议窗口的鼠标滚轮在当前布局中是否可靠必须在 DPI 感知修复后重新确认；此前“滚轮不可靠、拖动滚动条可靠”的部分观察受到坐标偏移污染。目录证据仍应以多张有重叠编号的截图覆盖，避免滚动跨度造成漏项。
- 长决议列表的“某项不存在”不能只凭单张当前视口断言。应拖动滚动条到明确的列表尾部，让最后一个预期 Mod 决议与紧随其后的原版决议同时入镜，再对 OCR 文本执行目标标题缺失检查。I1-003 的普通帝国和非机仆机械帝国均以“计划12 + 后续原版决议、无计划13”完成该负向夹具。

## 效果与存档断言

- 4.4.6 的“地产”页用于分公司/宗主持有关系，不是通用星球特征页，不能用它断言 `add_deposit`。
- 4.4 起岗位卡片的大号数字表示当前分配到该岗位的劳动力，不等于岗位最大容量。原版本地化 `EXPLAIN_WORKFORCE_NOT_LIMITED`/`EXPLAIN_WORKFORCE_OF_LIMIT` 明确把 `CURRENT`、玩家设置的 `LIMIT` 和脚本决定的 `MAX` 分开；因此新增空岗位后，大号数字可能保持不变。容量断言必须读取岗位劳动力滑块提示中的 `MAX`，或用存档与独立可见效果交叉证明，不能把“2.0K 仍是 2.0K”直接判为 modifier 失效。
- 运行 `20260906T105249Z` 中，计划13完成后星球住房从约 `5.7K` 增至约 `6.2K`，而活体陈设卡片仍显示 `2.0K` 当前劳动力；展开岗位行并悬停劳动力条后，提示明确给出当前 `2038`、最大上限 `2700`。这证明同一 deposit 的住房与 `+600` 岗位容量都已生效，也复现了“当前劳动力不是岗位容量”的界面陷阱。
- 对方舟的可靠效果断言是：决议队列出现且倒计时完成、适用区划上限或岗位数变化、存档 `gamestate` 中出现 deposit 键、重载后相同数值仍保持。
- 存档是 ZIP 容器，可只读检查其中的 `gamestate`。检查时同时断言 deposit 名称和出现次数，避免仅凭字符串存在误判。
- 存档 token 必须按引擎实际序列化文本匹配。PowerShell 会在启动子进程前处理命令行引号；若需要精确匹配 `type="..."`，优先把 token 放进声明式断言文件，或同时记录精确上下文与不含引号的保守 token，不能把 shell 丢失引号造成的零计数判为 deposit 缺失。
- 可用 `commands_at_date.txt` 在完成效果后的未来日期执行 `save <fixture-name>`，避免暂停菜单、中文输入法和文件名字符转换干扰存档生成。自动夹具应为存档记录路径、字节数、SHA-256、ZIP 成员，并对 `gamestate` 中的目标键做精确计数；只有实际产生文件才算保存成功。
- 中文输入法可能把自动输入的 ASCII 存档名转换为全角标点。本地夹具应按实际文件哈希定位存档，或先切换英文输入法；不要把预期文件名作为唯一成功条件。
- GUI 存档输入框不能假设物理 `Ctrl+A` 一定已取得文本焦点。运行 `20260906T105249Z` 的重复场景中，输入被追加成 `i1003_repeati1003_repeat.sav`；文件本身有效且哈希可验。自动回归应优先使用定时 `save`，必须走 GUI 时则先截图/OCR 确认字段内容，并始终用 SHA-256 识别夹具。
- 同一 `add_deposit` 第二次执行会创建新的 deposit 实例，而不是按 type 覆盖。计划13实测目标 token 从 `1` 增至 `2`，岗位 `MAX` 从 `2700` 增至 `3300`；重载后仍为 `3300`。重复语义必须同时断言实例数和玩家可见数值，不能只检查 token 存在。

## 日志归因

- 隔离 userdir 仍可能从启用文件中看到已订阅但本机缺失的其他 Workshop 路径。只有当前被测 Mod 的加载、脚本或运行错误才使 `LOAD-GREEN` 失败。
- `error.log` 的存档修复信息必须与重载后的 UI 数值和 `gamestate` 一起判断。若目标 deposit 仍唯一存在且效果保持，不能仅凭一次通用修复消息认定目标 deposit 丢失；该消息仍需记录并在后续回归中追踪。
- 对允许同名叠加的场景，上述判断要把“唯一存在”推广为“期望计数保持”：计划13重复执行存档重载时虽出现一次通用修复消息，但两个目标 deposit 与 `3300` 容量都保持，因此被清理的不是目标实例。
